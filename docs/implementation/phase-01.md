# Phase 01 — Foundation and canonical data contract

## Implemented

- Astro 7 static project with strict TypeScript, React islands, npm lockfile, Vitest, and Playwright.
- Full-viewport shared layout, navigation shell, persistent system-aware Day/Night theme, and specification-derived CSS tokens.
- Skeleton `/` and `/technical-cards` routes driven only by generated normalized data.
- Build-time local/GitHub source resolver, immutable commit snapshots, JSON Schema validation with Ajv 2020, normalization, deterministic joins, generated metadata, and source revision locking.
- Deterministic fixtures and unit/E2E tests, plus screenshot capture tooling.

## Canonical baseline

- Repository: `StefanoGiacomelli/torch_dae`
- Requested ref: `v0.2.0`
- Resolved commit: `fbc0fb9e470890f0e3f48b48e6effba69b71e39c`
- Discovered: 3 Model Cards and 9 Technical Cards
- Schema versions: Model Card `1.0.0`; Technical Card `1.0.0`

The local checkout lacks the tag object but contains the commit resolved from the public tag. `catalogue-source.json` records this reviewed release lock. Local mode resolves the tag or locked commit object and materializes it with `git archive` under `.cache/torch-dae-snapshots/<SHA>/`. It never ingests the working tree, so dirty changes and later source `HEAD` commits cannot affect the catalogue.

## Contracts and important files

- `src/data/types/catalogue.ts`: normalized frontend contracts.
- `src/data/types/raw.ts`: validated canonical input surface used by normalization.
- `src/data/ingest/`: source resolution, immutable snapshot materialization, recursive discovery, Ajv validation, raw-asset checks, and orchestration.
- `src/data/normalize/normalize.ts`: cross-card invariants, joins, unit conversion, and explicit energy semantics.
- `src/generated/catalogue.json`: ignored, deterministic-structure build output with a variable generation timestamp; regenerated by sync/prebuild.
- `catalogue-source.json`: release/ref/SHA lock.
- `src/styles/`: theme tokens and shared Phase 01 shell styles.

Model normalization retains checkpoint/acquisition identity, upstream sources, scientific references, datasets/evidence, architecture summary, and all canonical input constraints. Technical Card context retains protocol ID/version, structured hardware/software environment, execution-context fingerprint, runtime classification, backend/device, precision, thread regime, synthetic input, batch conditions, timing distributions, named memory surfaces, independent energy method/availability, and evidence/profiler provenance. Missing/partial energy remains `null`.

A Model Card may have zero linked Technical Cards. Technical Card → known Model Card integrity remains mandatory.

## Intentional Phase 01 limits

- Pages are data-proving skeletons, not the final carousel, selector, comparability, or chart UI.
- No chart library was installed because Phase 01 renders no charts; Phase 04 can choose the smallest suitable ECharts integration.
- Ajv strict-schema diagnostics are disabled for upstream-owned schemas; validation is Draft 2020, format-aware, and all-errors.
- Canonical v0.2.0 has no structured Model Card minimum duration, no designated default Technical Card, and no separate generic execution-regime field beyond the preserved runtime/thread/device context. Energy describes the resource pass rather than per-inference energy.

## Constraints to preserve

- Do not import raw canonical JSON from UI components; consume `CatalogueIndex`.
- Do not weaken immutable snapshotting, release-SHA verification, schema validation, ID uniqueness, unknown-model rejection, raw NPZ existence checks, or default-embedding reference checks.
- Do not collapse locally verified and upstream-declared device capability.
- Do not turn unavailable/partial energy into zero or collapse energy measurement method into coverage state.
- Do not collapse distinct CUDA/MPS memory observation kinds into one scalar.
- Keep `src/generated/` disposable and generated before build.
- Keep the canonical `torch-dae` checkout read-only.
